**Verdict:** not ready to release.

## Findings

**H1. `test-first.md`'s steps are broken.** The diff deleted step 6 (run
`tests-locked.sh`) and left the re-lock step numbered `.`, so three
references point to a "step 7" that doesn't exist. (Cause: a substitution
read `$17` as capture group 17.)

**H2. A genuine re-lock blesses earlier tampering.** Amendment 9's K2 and
criterion 54 lock the whole state at T2, including every implementer commit
after L1: a test weakened and the test command neutered before T2, then a
signed re-lock of another test, passes. The user signs believing they
approve one fix. A spec error.

**H3. A merged side branch's `lock.md` skips the chain (since 2.0.0).**
`git log -- lock.md` follows history simplification: a side branch with
weakened tests and an unsigned `lock.md`, merged with `-X theirs`, leaves
only the side's lock commit visible, so no sign-off is needed. main's
2.0.0 script passes it too, in CI as well.

**M1.** The re-lock's entry is unspecified for the Claude Code adapter: a
subagent can't stop for a sign-off between T2 and L2; `test-first`'s Output
still says "three commits" and its Autonomy omits the sign-off stop;
`cortex-test-writer.md` says "Edit only test and fixture files".

**M2.** The CHANGELOG and spec place the safeguard "in CI"; it is human
review of the test and config content in the pull request, which needs
branch protection with Code Owners (`INSTALL.md` 5b) and test paths in
CODEOWNERS.

**M3.** The review checklist doesn't mention a re-lock.

**Low.** L1: a lock commit that deletes `lock.md` exits 128 (a git error),
not 1. L2: a sign-off inside an HTML comment, or `n/a`, counts. L3: the
traps document's P6 still calls the test lock absolute. L4: README status
and install tag, and the CHANGELOG's missing "Before release" list. L5: a
double blank line. L6: a re-lock can drop a file the earlier lock listed.

**Nomination:** the re-lock procedure is written out three times (the
`lock.md` template comment, the script header, `test-first` step 7); keep
step 7 and point to it.

## Decisions and follow-up

Found while planning the fixes, and reproduced: **H3b.** A merged side
branch that only weakens a test, with `lock.md` untouched, passes:
Amendment 4's allowance accepts any merged parent's version, not only the
base's (since 2.0.0, in CI too).

The maintainer chose to fix the 2.0.0 holes in 2.1.0, with a security note
on 2.0.0. Spec Amendment 10 corrects Amendment 9 (a re-lock blesses only its
own tests commit), makes lock history first-parent (H3), limits the base

sets (H3b), requires a re-lock to keep the earlier list (L6), and fails a
deleted `lock.md` cleanly (L1). H1, M1, M2, L3-L5 and the nomination are
fixed in the same branch. Recorded as known, not changed: M3 (the mechanical
H2 fix covers the risk, and a checklist edit would trigger the golden runs)
and L2 (the sign-off is free text either way). The audit is re-run before
release.

## Re-run on the corrected branch (`f7db23d`)

A fresh agent re-ran the audit on Amendment 10's fixes, probing by hand.
The first audit's findings are resolved or recorded as known (M3, L2). New:

- **H1 (also in 2.0.0).** In CI, a merge whose merged parent is any base
  ancestor can restore the pre-lock version of a locked file or config:
  resolve a real base merge to the base's (older) copy, or fabricate a
  merge with the fork point as a parent. The file then equals the base, so
  it vanishes from the pull request's diff. Amendment 10's L3 asked only
  whether the content came from the base, not whether the base changed it.
- **M1.** A branch can switch off the CI lock by deleting its change folder
  or moving it under `changes/archive/`.
- **M2.** A re-lock's tests commit can change `.cortex/config` and narrow
  `TEST_GLOBS`, unlocking files no sign-off covers.
- **Low.** README status and install tag; the adapter's re-lock drops the
  criteria-to-tests update; script headers drifted; a catalog citation.
- **Nominations.** One function for the lock set; limit the archive
  exemption to locks already on the base.

**Decision (maintainer):** each audit round had found a new hole in the
same rule, the base-merge allowance (Amendment 4), as R11 warns of rules
narrowed by reasoning about input shapes. Rather than narrow it again,
Amendment 11 deletes it: a change to a locked file not made in a signed
re-lock's tests commit fails, merges included, and bringing a locked
branch up to date with a base that changed locked files means merging and
then re-locking. It also fails a lock removed or archived on its own
branch (M1) and a re-lock that changes `.cortex/config` (M2).

## Focused re-check of Amendment 12 (`ba49af7`), 2026-10-04

A fresh agent mapped Amendment 12 and the third round to evidence and
probed step 4 in scratch repositories. The process rule held (spec, then
tests-only commits, then the script). New:

- **H-a, H-b (reproduced; regressions of `85f2168`).** The exemption for
  any path the base's history had was keyed on the path, passed to git as a
  pattern: a folder named `changes/[o]ld` or `*` matched a lock the base
  once had, and a branch reusing a folder name the base had archived could
  drop its lock. The script before Amendment 12 caught both. N1 now says a
  lock is the branch's when some branch commit has the path and none of its
  parents does, checked literally against `HEAD` and the base tip (criteria
  76-77, tests first, `9dec7d4`); the re-check's probes, rerun, all behave
  as specified.
- **Low.** The CHANGELOG overstated the check (fixed); criterion 62's text
  still names `CORTEX_BASE_REF` (N1 notes it; left, since the criterion
  stands); `test-first` step 7 didn't say to undo the merge (fixed).
- **Recorded as known, not changed (both predate 2.1.0):** L-d, reusing a
  folder name the base used, with the lock kept, fails `tests-locked.sh`
  (the base's commits on that path count as lock commits; `spec-new`'s
  dated folder names make it unlikely); L-e, a lock added directly under
  `changes/archive/` is never gated (no command puts one there, and the
  change's tests then show as unlocked in review).
