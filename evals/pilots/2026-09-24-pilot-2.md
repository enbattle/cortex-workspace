# Pilot 2: the Claude Code adapter, headless, 2026-09-24

Pilot 1 could not test the Claude Code adapter because the toy repo's
subagent types were not registered in the session that ran it. This pilot
ran the three role-separated skills (`cortex-test-first`,
`cortex-implement`, `cortex-review`) as three separate headless Claude Code
sessions started from inside an installed repository. For each one it checks
from the stream-json that the skill loaded and handed the work to its named
subagent.

## Setup

- **Repository:** a clone of `evals/golden/review-maxlength/fixture.bundle`
  (`slugkit`, cortex 2.0.0 installed).
- **Branch:** `slugify-maxlength`, recreated at `11a7112` ("spec: approved
  change folder ..."). That is the commit before test-first's tests, so the
  repo was at "spec approved, no tests yet". The tags and the `origin`
  remote were deleted, and a local git identity (`pilot2`) was set.
- **Adapter files:** `.claude/agents/cortex-{test-writer,implementer,reviewer,security-reviewer}.md`,
  `.claude/skills/cortex-*/SKILL.md` and `.claude/settings.json` were all
  present. They are byte-identical to the current
  `template/.cortex/adapters/claude-code/.claude/`, so `adapt.sh` was not
  re-run.
- **Harness drift:** the fixture's `harness/commands/review.md` and
  `spec-new.md` are older than the working-tree template. The only
  difference is the uncommitted edits to review.md step 1 (probe scripts go
  in a scratch directory) and step 2 (`origin/<default>` in a fresh clone).
  The reviewer therefore ran the fixture's older review.md.
- **Tooling:** Claude Code 2.1.281, model `claude-opus-5-5`.
- **Invocation:** each session ran from the repo root as:
  `claude -p "Run the cortex-<skill> skill for change folder changes/20260924-slugify-maxlength." --output-format stream-json --verbose --forward-subagent-text --permission-mode acceptEdits --allowedTools Skill Agent Task Read Edit Write Glob Grep "Bash(git *)" "Bash(node *)" "Bash(bash scripts/cortex/*)"`.
  With `-p`, any command that would prompt is denied automatically.
- **Logs:** the stream-json logs (`s1-test-first.jsonl`, `s2-implement.jsonl`,
  `s3-review.jsonl`) and `analyze.js` were kept in the operator's scratch
  directory. They are not committed.

All three sessions exited 0 on the first try; no retry was needed.

## Delegation evidence (from stream-json)

In every session the main-session tool sequence was the same: first
`Skill {"skill":"cortex-<name>","args":"changes/20260924-slugify-maxlength"}`,
then exactly one `Agent` call with the right `subagent_type`. The `prompt`
was only the folder path, as the skill says, and `run_in_background` was
false. No session used a fork or a `general-purpose` agent. The init
message listed all four `cortex-*` agents and all seven `cortex-*` skills.

| Session | Agent call | Tool calls inside the subagent (`parent_tool_use_id`) | Main session did itself |
| --- | --- | --- | --- |
| 1 | `subagent_type: cortex-test-writer` | 23 (Read, Write, Edit, Bash: wrote the test file, committed it, wrote and committed lock.md, then tasks.md) | `tests-locked.sh`, `node --test`, `git log`, a Grep on the approval line. Checking only, no edits. |
| 2 | `subagent_type: cortex-implementer` | 21 (Write/Edit `src/slugify.js`, `tasks.md`, 4 commits) | `gates.sh`, run twice (see F2), `git status`/`log` |
| 3 | `subagent_type: cortex-reviewer` | 22 (Read and Bash only: gates, diff, node probes, git status) | `git status --porcelain -uall` before and after the Agent call, then **Write** `review-findings.md` |

**Reviewer and Edit/Write.**
- The reviewer made no Edit, Write or NotebookEdit calls. The only Write in
  session 3 is the main session writing `review-findings.md`, which the
  adapter intends.
- The agent file limits the reviewer to `tools: Read, Grep, Glob, Bash`.
- The stream-json does not list a subagent's own tool set, so this pilot
  shows that Edit/Write went unused. It does not show that they were
  unavailable.
- The reviewer's Bash calls were all read-only (git status/diff/ls-files,
  gates, `node --input-type=module -e ...` probes). It wrote no probe files.

## Friction

Each item gives the evidence, then the cortex file involved, then the
proposed fix.

- **F1. Subagents use compound Bash commands that allowlists can't match.**
  - **Evidence:** 9 automatic denials across the three sessions (3, 2, 4).
    Subagents caused 7 (2, 1, 4) and main sessions caused 2 (one each in
    sessions 1 and 2; see F2). Every one was a compound command such as
    `cd "<abs repo>" && cat a b c; echo ----; git log`. Session 3 got
    "Claude requested permissions to use Bash" for
    `git -C "<abs repo>" merge-base HEAD main`. It also got "cat reads a file
    by a relative path after a cd in a compound command ... while a Read()
    deny rule is configured, so this needs approval". That message is
    caused by the template's own `Read(./**/.env)` deny rules.
  - **Impact:** each agent recovered by using Read or a simpler command, so
    nothing was blocked. Interactively, though, each of these would be a
    permission prompt.
  - **Files:** `template/.cortex/adapters/claude-code/.claude/agents/cortex-*.md`
    and `.../.claude/settings.json`.
  - **Fix:** add a line to each agent file: "Your working directory is the
    repository root: run one command per Bash call, without `cd`, `;`,
    `&&` or `echo`, and use Read for files." Also consider having
    `settings.json` (or `adapt.sh`, from `.cortex/config`) add an `allow`
    list:
    - `Bash(bash scripts/cortex/*)`
    - the `TEST_CMD`/`BUILD_CMD`/`LINT_CMD` values
    - read-only git (`git status*`, `git diff*`, `git log*`, `git merge-base*`,
      `git ls-files*`)

- **F2. The skill's own script runs in the main session were denied first.**
  - **Evidence:** session 2's first `gates.sh` call
    (`...; echo "exit=$?"; git status --short; ...`) was denied. It was
    re-run bare and succeeded. The same happened in session 1 with
    `cd <repo> && bash scripts/cortex/tests-locked.sh ...`.
  - **File:** `template/.cortex/adapters/claude-code/.claude/skills/cortex-{implement,test-first}/SKILL.md`.
  - **Fix:** have the skill say to run the script as a single command, with
    nothing chained after it.

- **F3. After review, `review-findings.md` is left untracked.**
  - **Evidence:** the status after session 3 is
    `?? changes/.../review-findings.md`.
  - **Why it matters:** round 2 of `review` requires a clean tree, and
    `implement.md` doesn't say to commit the findings.
  - **Who owns the commit:** nobody. `review.md` says the calling session
    "writes the file and does nothing else".
  - **Files:** `template/.cortex/adapters/claude-code/.claude/skills/cortex-review/SKILL.md`,
    plus `template/harness/commands/review.md` (Output) or `implement.md`
    (step 1).
  - **Fix:** either the review skill commits `review-findings.md` alone
    (`review: round <n> findings`), or implement step 1 commits it before
    starting. Pick one and state it in both files.

- **F4. The skill's before/after check misses edits made after the Agent call.**
  - **Evidence:** in session 3 the "after" status was taken before the main
    session's Write. That is correct for isolating the reviewer. But
    nothing records that the only permitted difference is
    `review-findings.md`.
  - **File:** `.../skills/cortex-review/SKILL.md`.
  - **Fix:** add "after writing the file, the only difference from the
    before state may be `review-findings.md`."

- **F5. The pilot cannot confirm whether the reviewer had Edit/Write.**
  - **Evidence:** the stream-json shows the reviewer's tool calls but not
    the tools it was given.
  - **File:** `evals/golden/review-maxlength/README.md` (the adapter re-run
    procedure).
  - **Fix:** to prove the restriction, add a probe run where the reviewer
    is told to create a scratch file with Write and must report the tool as
    unavailable. Keep it out of real reviews.

- **F6. The golden fixture's harness is behind the template.**
  - **Evidence:** the `review.md` and `spec-new.md` diffs described under
    Setup.
  - **File:** `evals/golden/review-maxlength/fixture.bundle`.
  - **Fix:** rebuild the bundle when the template's review.md edits are
    committed, or note in the README which template commit the fixture
    matches.

- **F7. Connector noise (not cortex).**
  - **Evidence:** all three final messages end with a request to authorize
    the claude.ai Gmail, Calendar and Drive connectors. That comes from the
    operator's environment.
  - **Fix:** none in cortex. For clean runs, the pilot procedure could add
    `--strict-mcp-config`.

## Verdict

On this run the adapter does what the README claims:

- Each skill loaded.
- Each role went to its named `cortex-*` subagent, never a fork or the main
  session.
- The test lock held through implement.
- Gates passed.
- The read-only reviewer made no edits and returned a well-founded request
  changes.

The remaining problems are permission friction from compound Bash commands
(F1, F2) and the uncommitted findings file (F3). The adapter should be
re-run interactively once F1 is fixed to count the real prompts.
