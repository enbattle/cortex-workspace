# Pilot 3b — pilot 3 again, after its fixes, 2026-10-03

Same setup as pilot 3 (`2026-10-03-pilot-3.md`): slugkit's original
library, cortex installed per `INSTALL.md`, one session per stage, headless,
on Windows 11 with claude-opus-5-5. Differences:

- **cortex:** pilot 3's fixes (the allow list, one command per call, the
  narrowed merge rule, done-checks) and the new approval step (R6's
  instructed fill-in, the independent spec brief), from the branches that
  became the pull requests after this one.
- **Permissions:** pilot 2's extra `--allowedTools` were dropped. Only the
  shipped `settings.json`, the project's `node --test` and `node --check`
  (added per `INSTALL.md`), and `--permission-mode acceptEdits` applied, so
  each denial is a prompt a person who followed the install would see.
- **Change:** new to every agent: a `lowercase` flag for `slugify`.

## Findings

- **P7. `git checkout -b` wasn't allowed** (agents create branches that way).
  Fixed during the run: allowed for Bash and PowerShell.
- **P8. Committed `allow` rules wait for folder trust.** Claude Code applies
  a committed `.claude/settings.json`'s `allow` rules only after each person
  trusts the folder, so a headless run in an untrusted folder got none of
  them (the first `spec-new` denied `git checkout -b` with the rule present).
  The pilot then put the same rules in the untracked
  `.claude/settings.local.json`, which applies without trust.
- **P9. An instructed approval needs a record another session can trust.**
  The operator wrote the line on the owner's explicit instruction (allowed
  by R6); the `spec-clarify` session, which had just refused a relayed
  approval, couldn't tell it from a forged one and declined to commit. The
  operator committed it with the instruction quoted. Later, a spec amended
  after approval kept its old approval line (review L2).
- **P10. A spec planned an edit to a locked file.** The owner's version bump
  edits `package.json`, which `TEST_GLOBS` locks (as `INSTALL.md` advises),
  so `implement` couldn't do it. The owner dropped it and re-approved.
- **P11. `git -C <path>` slips past the allow patterns** (`git log*` doesn't
  match `git -C x log`).
- **P12. The real-artifact check runs arbitrary code**, so it prompts, and a
  headless run can't answer. Both `implement` and `review` were blocked;
  the person ran the reviewer's command and it printed the expected
  values. Allowing `node` outright would let agents run any code unasked.
  (Revised by the release audit, `evals/audits/2026-10-03.md` M3: agents
  already run code they wrote through the allowed test command and gates,
  so this protection wasn't real. `INSTALL.md` now advises allowing the
  project's run command.)

## Fixes (this pull request)

- P8: `INSTALL.md` says committed allow rules wait for folder trust, and
  what a headless run uses instead.
- P9: R6 and `spec-clarify` step 6: the agent that fills in the line on
