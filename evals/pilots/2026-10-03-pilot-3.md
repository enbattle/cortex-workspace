# Pilot 3 — the whole pipeline on a new change, counting prompts, 2026-10-03

The release list's last item: one run through the pipeline counting the
permission prompts a person would see, after pilot 2's F1 fix. Run headless
(the maintainer chose this over an interactive session): with `-p`, every
call that would prompt is denied and logged, so denials count prompts.

## Setup

- **Repository:** `slugkit`'s original 12-line library and its 4 tests, in a
  throwaway repository; cortex installed from `main` at `570e0ab` following
  `INSTALL.md` (install branch merged into `main`; the operator filled in
  config, `AGENTS.md`, the constitution's P1-P3 and the knowledge stubs;
  `check.sh` ok).
- **Change:** new to every agent: an optional `separator` for `slugify`.
- **Invocation:** pilot 2's exact flags, so the denial counts compare:
  `claude -p "<prompt>" --output-format stream-json --verbose --forward-subagent-text --strict-mcp-config --permission-mode acceptEdits --allowedTools Skill Agent Task Read Edit Write Glob Grep "Bash(git *)" "Bash(node *)" "Bash(bash scripts/cortex/*)"`,
  one session per stage (resumed to answer a stage's questions), on
  Windows 11, model claude-opus-5-5.
- **Roles:** the operator answered the product questions acting as the
  user, as in pilot 1. **The maintainer wrote the approval line himself**
  (pilot 2's operator had written it), after a plain-language brief of the
  change.

## Findings

- **P1. F1 worked for subagents.** Subagent denials went from 7 (pilot 2,
  all compound commands) to 1 in 110 subagent calls, and that one wasn't
  compound.
- **P2. The main session still chains commands.** 3 denials in `spec-new`
  and `spec-clarify` (`cd ... && git ls-files | grep ...; echo ...`). F1's
  line is in the agent definitions only; these stages run in the main
  session, which never reads them.
- **P3. PowerShell isn't covered.** 3 denials were PowerShell calls (the
  agent's Windows shell), which the allow list didn't name. A Windows user
  sees those as prompts too; the shipped `settings.json` already lists
  PowerShell in its deny and ask rules, so PowerShell use is expected.
- **P4. A plain `git merge-base HEAD main` by the reviewer was denied**
  although `Bash(git *)` should match it; pilot 2 saw the same command
  prompt. Cause, found while fixing P5: the shipped `ask` rule
  `Bash(git*merge*)`, meant for `git merge`, also matches `git merge-base`,
  and an `ask` rule wins over an `allow`.
- **P5. With only the shipped settings, a person would face about 100
  prompts.** The run made 64 shell calls and 39 edits; the shipped
  `settings.json` denies and asks but allows nothing, so in default mode each
  would prompt unless the person keeps choosing "always allow" or turns on
  auto-accept for edits. Pilot 2 suggested shipping an allow list; this is
  the evidence for it.
- **P6. `spec-clarify` writes done-checks that can't pass mid-change**
  (found by the retro). Task 1's check was "the four existing tests pass
  (`npm test`)", but by then the locked failing tests are in the suite, so
  the whole test command fails until the last task; the implementer ran a
  test-name pattern instead.

## Proposed fixes (for the maintainer)

- P2: a tool-neutral line in the template's `AGENTS.md` (read by every
  session): run one shell command per call, without chaining, since
  permission rules match single commands.
- P3, P5: ship an allow list in the Claude Code adapter's `settings.json`
  for the read-only and routine commands the pipeline runs (`git status`,
  `diff`, `log`, `show`, `ls-files`, `merge-base`, `add`, `commit`;
  `bash scripts/cortex/*`), for both Bash and PowerShell, and say in
  `INSTALL.md` how to allow the project's own build, test and lint
  commands. Re-run this pilot to count again.
- P6: one sentence in `spec-clarify.md`: an intermediate done-check names
  the tests it runs, not the whole test command.
- P4: narrow the `ask` rule to `git merge <args>` and `git <options> merge <args>`.
