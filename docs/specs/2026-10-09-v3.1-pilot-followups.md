# Plan: the release-candidate pilot's follow-ups (3.1.0)

Status: **approved by the maintainer, 2026-10-10.** A point-in-time
record: the completeness audit maps every item below to evidence.

## Context

The 3.0.0 pilot (`evals/pilots/2026-10-09-rc-pilot-til.md`, findings R1–R8)
and the release audit (`evals/audits/2026-10-09.md`) left follow-ups. On
2026-10-09 the maintainer gave the go-ahead to fix all of them. This plan
says how. Each script change gets tests from a separate agent, committed
before the script changes.

R1 is closed without a change. An upgrade didn't record a `.prettierignore`
line added by hand under rc.1. That can only happen to an rc.1 install, and
none remain (the pilot's branches are deleted). An install from rc.2 on
records the line whenever it asks for it.

## Items

### G1. One rule for "`.prettierignore` already ignores cortex" (audit finding 4, nomination 3)

- `_footprint.sh` gains `prettierignore_has FILE`. It is true when some line
  of FILE, after dropping a carriage return and surrounding spaces and tabs,
  is exactly `cortex`, `/cortex`, `cortex/` or `/cortex/`.
- `adapt.sh` (asking for the line), C13 (the recorded
  `entry .prettierignore cortex/`) and `remove.sh` step 2 all use it.
  - C13 passes if the file has any of the four forms, and fails if it has
    none. A line like `src/cortex/x` doesn't count.
  - Other entries (`.claude/settings.json`) keep their current rule.
- `remove.sh` step 2 doesn't list `.prettierignore` lines in any of the four
  forms as references when that entry is recorded.

### G2. A reworded placeholder doesn't conflict with a filled-in section (R2)

- An upgrade's three-way merge may conflict. If **every** conflicting hunk
  is a placeholder hunk, the file takes the user's side of each hunk, and
  the upgrade prints `merged <path> (kept your text where cortex changed a
  placeholder)`. It counts as merged, not as a conflict.
  - A placeholder hunk is one where both the installed version's text and
    the new version's text are only HTML comments and blank lines.
  - The HTML comments may span lines, and there must be at least one.
- If any conflicting hunk is not a placeholder hunk, the output is exactly
  as in 3.0.0: every hunk keeps its conflict markers, in the same format.
- This applies to file merges and to the root agents block's merge alike.

### G3. Gates fail on an open task (R3)

- `gates.sh` gains a gate, `tasks`, which runs after `tests-locked` and
  before `build`. It fails when `<change-folder>/tasks.md` is missing, or
  has an open task (a line `- [ ]` or `* [ ]`, at any indentation) before
  its first `## ` heading. Its output names each open task's line number
  and text, then prints `gate tasks: FAIL (exit 1)`. Otherwise it prints
  `gate tasks: ok`.
  - Lines under the later headings (Manual verification and the rest)
    don't count.
- `ci-gates.sh` runs `gates.sh`, so CI fails on a pull request whose change
  still has open tasks.
- `spec-clarify` writes no task for running the gates or review, since
  implement's step 6 and review do those. `implement` step 6 says the
  tasks gate fails on any task it left unticked.

### G4. Review's verdict is recorded (R4)

- Every review round is recorded in `review-findings.md` as a section
  `## Round <n>`, an approval included.
  - Its first line is `Verdict: approve at <commit>, <date>.` or
    `Verdict: request changes at <commit>, <date>.`.
  - An approval adds the paragraph on what was probed and found sound.
- The file is committed alone, as now, by the reviewer or the session that
  started it.
- The round budget counts `request changes` rounds.
- `implement` step 1's "open findings" means a request-changes round with
  findings not yet triaged.
- `retro` reads the verdict from the file.

### G5. Review reads the project's own instructions (R5)

- Review's inputs gain the project's agent instructions that the router
  names: the root `AGENTS.md` outside cortex's block, and a `CLAUDE.md` or
  other tool file outside cortex's block.
- `implement`'s preconditions load the same files.
- Because this edits `review.md`, the golden cycle runs twice with fresh
  reviewers (AGENTS.md).

### G6. Pipeline wording (R6, R7; audit finding 5's sibling)

- `spec-new` step 1 creates the branch from an up-to-date default branch,
  unless the user names another base (for example, while cortex's own
  install is still on an unmerged branch).
- In the router's "One shell command per call" rule, if the shell isn't at
  the repository root, a plain `cd` to the root, alone in its own call,
  comes first.
- `spec-clarify` step 6: "I approve", with nothing about who writes the
  line, is approval of the spec, not an instruction to write the line. Ask
  whether they will write it or want you to.
- `retro` step 5: wait for the user's answer on every proposal before
  step 6. The pipeline-log row records the answers, so it is written after
  them.

### G7. Removal points references at the kept records (R8)

- In `remove.sh` step 2, a reference that names a path the records step
  will keep gets a second line: `  kept as <records-dir>/<rest>`.
  - The kept paths are under `cortex/changes/` or `cortex/knowledge/`, or
    `cortex/constitution.md`.
  - `<records-dir>` is the directory step 3 will use (default
    `docs/cortex-records`, or `--keep-records <dir>`).
  - With `--delete-records` there is no second line.

### G8. Deletions and merges (audit nominations 1, 2)

- `block_unedited`'s fallback for a record without the sixth field goes, as
  does the header note about it.
  - A record without `nb` is unedited only if its sha matches.
- INSTALL step 3's item 0 (the project's own process) merges into item 9
  (Conventions), as the first thing that item asks.

### G9. Tests for the untested F5 items (audit finding 8)

- Install from a template clone where no file is executable (as on Windows)
  still marks exactly the scripts named by `cortex/bin/*.sh` minus `_*.sh`
  executable, and the note names them.
- G1's tests cover the `.prettierignore` forms.

## Acceptance criteria

1. G1: adapt prints no merge line, and records nothing, for each of the four
   forms (CRLF and surrounding spaces too). For `src/cortex/x` it asks.
2. G1: with the entry recorded, C13 passes for each form and fails when no
   form is present, `src/cortex/x` included.
3. G1: remove step 2 lists no reference for a `.prettierignore` line in any
   of the four forms when the entry is recorded.
4. G2: an upgrade where the user replaced a placeholder comment that the
   new version rewords gives `merged ... (kept your text ...)`, exit 0, and
   the user's text with no markers.
5. G2: the same file with a second, real conflicting hunk gives the 3.0.0
   output, both hunks with markers, `conflict <path>` and exit 1.
6. G2: a conflict where only one side is a placeholder is a real conflict.
7. G2: the root agents block's merge follows criteria 4 and 5.
8. G3: open tasks:
   - `- [ ]`, `* [ ]`, indented, and a missing `tasks.md` each fail the
     tasks gate, listing each open task.
   - `- [x]`, `- [X]`, and `- [ ]` under a later `## ` heading pass.
   - Every other gate still runs (`gates: N failed`).
9. G3: the gate order is tests-locked, tasks, build, test, lint, check.
10. G3: ci-gates fails a pull request whose locked change folder has an open
    task, and passes it once the task is ticked.
11. G4, G6 and G5 are wording: the completeness audit checks them, and the
    golden cycle runs twice.
12. G7: a reference to `cortex/changes/x/proposal.md` prints
    `  kept as docs/cortex-records/changes/x/proposal.md`.
    - With `--keep-records <d>` it prints `<d>/...`.
    - With `--delete-records`, nothing.
    - A reference to `cortex/bin/gates.sh` prints nothing.
13. G8: removal of a block recorded without `nb` and changed only in blank
    lines shows it as edited. Unchanged, it is removed.
14. G9: the mode-less clone case of the install suite.
15. Existing suites pass. An assertion changes only where this plan changes
    the behavior it asserts (gate lists and counts, G3), and each such
    change is named in the tests' commit message.

## Release

- `VERSION` 3.1.0 (new checks and behavior, nothing removed from a
  command's contract).
- A CHANGELOG entry, with notes for installed repositories: after
  upgrading, open tasks fail the gates.
- The golden fixture refreshed, the golden cycle twice, a completeness
  audit, then the tag.

## As built

- Criterion 13 said a block shown as edited is "(kept)". Removal shows an
  edited block and then removes it anyway (3.0.0 criterion 18), and G8
  doesn't change that, so the word was wrong and is dropped. The tests
  (`692867b`) assert that the block is shown as edited, not that it is kept.
  Raised by the test writer.
- The completeness audit (`evals/audits/2026-10-10.md`) found two defects
  in the new code. Both are fixed under the plan's own intent, with tests
  first:
  - **G2's parser.** It recognizes only the merge's own labelled markers:
    `<<<<<<< <path> (yours)`, `||||||| <path> (cortex <installed>)`,
    `=======`, and `>>>>>>> <path> (cortex <new>)`.
    - Any other line, one starting `<<<<<<< ` included, is content.
    - A conflict still open at the end of the file means the placeholder
      merge fails, so the 3.0.0 output stands.
    - Criterion 16: a user line `<<<<<<< HEAD`, above or below a
      placeholder hunk, is kept intact. It is reported, and C14 still
      flags it.
  - **G7's paths.**
    - A `cortex/` preceded by `/` (as in `docs/cortex/changes/x.md`) is a
      project path, so it gets no kept line.
    - A `#fragment` or `?query` after a kept path is dropped from the kept
      line.
    - Criterion 17: `docs/cortex/changes/old.md` prints no kept line;
      `cortex/constitution.md#project` prints
      `  kept as <records-dir>/constitution.md`.
