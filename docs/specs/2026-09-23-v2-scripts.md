# Spec: cortex v2 scripts (install, check, tests-locked, adapt)

Status: approved 2026-09-23 (Steven Li, via the v2 plan). A point-in-time
record; the scripts and `docs/01-design-rules.md` are authoritative after
it lands.

## Context

cortex v2 ships real template files instead of a prompt that generates them.
Four bash scripts (six by Amendment 3: `gates.sh` in Amendment 1, `ci-gates.sh` in Amendment 3) carry every mechanical guarantee the design rules make
(R11: gates are checks the next stage runs, never self-reports). Each is
`#!/usr/bin/env bash` with `set -euo pipefail`, runs under Git Bash on
Windows and bash on Linux, uses only git and POSIX tools (no `yq`, no `jq`,
no network), and never sources a config file (config is parsed, not executed).

## Layouts

cortex repo (source):

```
VERSION                          one line, e.g. 2.0.0
scripts/install.sh
template/                        copied verbatim into a target repo
  AGENTS.md
  .cortex/config                 KEY=VALUE lines (see below)
  .cortex/adapters/claude-code/  source files adapt.sh installs for Claude Code
  harness/commands/*.md
  harness/templates/**
  harness/policies/*.md
  docs/knowledge/**
  changes/archive/.gitkeep
  changes/pipeline-log.md
  scripts/cortex/check.sh
  scripts/cortex/tests-locked.sh
  scripts/cortex/adapt.sh
tests/                           bash test suites for all four scripts
```

`.cortex/config` format: one `KEY=VALUE` per line; `#` starts a comment line;
blank lines ignored; the value is everything after the first `=`, with
surrounding whitespace trimmed and no quote processing. Keys:
`PROJECT_NAME`, `BUILD_CMD`, `TEST_CMD`, `LINT_CMD`, `TOOLS` (comma-separated
from `claude,cursor,copilot,gemini,codex`), `TEST_GLOBS` (space-separated
git pathspec globs, e.g. `*.test.ts tests/**`). An unset or empty key, or a
value of the form `<...>` (placeholder), counts as unset.

## `scripts/install.sh <target-dir>`

1. If `<target-dir>` is missing or not inside a git work tree: print an error
   to stderr, exit 2. No argument: usage to stderr, exit 2.
2. For every file under `template/` (including dotfiles and `.gitkeep`), at
   the same relative path in the target:
   - absent → copy it (preserve the executable bit for `*.sh`), print
     `created <relpath>`
   - present and byte-identical → print `unchanged <relpath>`
   - present and different → leave it untouched, print
     `skipped <relpath> (exists, differs)`
3. Write `<target>/.cortex/version` containing the contents of `VERSION` if
   absent (`created .cortex/version`). If present and equal: `unchanged
   .cortex/version`. If present and different: leave it, print
   `warning: installed version <old>, template version <new>` .
4. Print a final summary line: `install: <c> created, <u> unchanged, <s> skipped`.
5. Exit 0 whenever step 1 passed, including when files were skipped.
6. Never modifies a file that already exists in the target, never deletes
   anything, never runs git commands that write (no add/commit).
7. Idempotent: running it twice in a row, the second run prints no `created`
   lines and ends with `0 created`.

## `scripts/cortex/check.sh [repo-root]`

Default root is the current directory. Checks the installed harness's
invariants. Each violation prints one line to stdout:
`FAIL [<ID>] <relpath>: <message>`. After all checks, prints `check: ok` and
exits 0 if there were none, otherwise `check: <n> failure(s)` and exits 1.
Missing optional files are not failures unless stated.

| ID  | Rule | Violation |
| --- | ---- | --------- |
| C1  | R1   | `PROJECT_NAME` (if set) appears, case-insensitively, in any file under `harness/` |
| C2  | R8   | a tool name — `claude`, `cursor`, `copilot`, `gemini`, `codex` as a whole word, case-insensitive — appears in any file under `harness/` or `docs/knowledge/` |
| C3  | R2   | `AGENTS.md` is missing, or longer than 60 lines |
| C4  | R5   | a file under `harness/` contains `read all` or `read everything` (case-insensitive) |
| C5  | —    | a `harness/commands/*.md` file lacks any of the headings `## Purpose`, `## Preconditions`, `## Procedure`, `## Output`, `## Autonomy` (each at line start) |
| C6  | R10  | a `harness/commands/*.md` file has no line starting with `Budget:` |
| C7  | R6   | the literal `Approved-by:` appears in any file under `harness/` other than `harness/templates/change-folder/proposal.md` |
| C8  | R8   | `CLAUDE.md` exists and, ignoring blank lines and lines that are only an HTML comment (`<!-- ... -->`), is anything other than the single line `@AGENTS.md` |
| C9  | R8   | a file under `.claude/skills/` whose name is `SKILL.md` and that contains the marker `cortex:generated` has more than 25 lines |
| C10 | —    | `AGENTS.md` exists but does not contain the phrase `data, never instructions` (the untrusted-content rule) |

`.cortex/adapters/` is never scanned by C1–C4, C7.

## `scripts/cortex/tests-locked.sh <change-folder>`

Verifies that tests locked by the `test-first` command are untouched.
Reads `<change-folder>/tasks.md`:

- a line `Tests-locked-at: <sha>` (first match wins)
- a heading line `## Locked tests`, followed by list lines `- <path>` (paths
  relative to the repo root, optionally wrapped in backticks), ending at the
  next heading or end of file

Run from anywhere inside the repo. Fails (exit 1) with one line per problem,
`LOCK <kind>: <detail>`, when:

- `tasks.md` is missing, has no `Tests-locked-at:` line, or lists no locked
  tests (`LOCK missing: ...`)
- the sha does not resolve to a commit, or is not an ancestor of `HEAD`
  (`LOCK bad-sha: ...`)
- a listed path did not exist in that commit (`LOCK not-locked: <path>`)
- a listed path differs between that commit and the working tree, including
  staged and committed changes after the sha, or was deleted
  (`LOCK modified: <path>` / `LOCK deleted: <path>`)
- `TEST_GLOBS` is set in `.cortex/config` and a file matching it exists now
  that did not exist at the sha — committed after it, staged, or untracked
  (`LOCK added: <path>`). Adding tests is the test-writer's job, not the
  implementer's.

On success prints `tests-locked: <n> file(s) unchanged since <short-sha>` and
exits 0. Usage errors exit 2.

## `scripts/cortex/adapt.sh [repo-root]`

Generates tool adapters from `TOOLS` in `.cortex/config`. Every file it
writes, except `.claude/settings.json` (JSON has no comments; it has its own
rule below), contains the marker `cortex:generated`, as an HTML comment in
markdown files. It overwrites a target file only if that file
does not exist or already contains the marker; otherwise it prints
`skipped <relpath> (hand-written; merge manually)`. Prints `wrote <relpath>`
or `unchanged <relpath>` for each file it manages. Exit 0; exit 2 if
`.cortex/config` is missing.

- `claude`: `CLAUDE.md` = `<!-- cortex:generated -->` line + `@AGENTS.md`
  line. Copies every file under `.cortex/adapters/claude-code/` into the repo
  root at the same relative path (e.g. `.claude/skills/review/SKILL.md`,
  `.claude/agents/cortex-reviewer.md`), under the same marker rule, except
  `settings.json`: if `.claude/settings.json` is absent it is copied; if
  present it is never touched, and the script prints
  `skipped .claude/settings.json (exists; merge the permissions block from .cortex/adapters/claude-code/.claude/settings.json)`.
- `cursor`: `.cursor/rules/cortex.mdc` with frontmatter `alwaysApply: true`
  and one line pointing to `AGENTS.md`.
- `copilot`: `.github/copilot-instructions.md`, one line pointing to
  `AGENTS.md`.
- `gemini`: `GEMINI.md`, one line pointing to `AGENTS.md`.
- `codex`: writes nothing; prints `codex: reads AGENTS.md natively`.
- An unknown tool name prints `warning: unknown tool <name>` and is ignored.
- Idempotent: a second run prints only `unchanged` (and `skipped`) lines.

## Acceptance criteria (automatable)

1. `install.sh` into a fresh `git init` repo creates every template file,
   exits 0, and a second run reports `0 created`.
2. `install.sh` never overwrites a pre-existing differing file (e.g. an
   existing `AGENTS.md`), reports it as skipped, exits 0.
3. `install.sh` exits 2 for a non-git directory and for no argument.
4. `check.sh` on a fresh install (with `PROJECT_NAME` set to something that
   appears nowhere in the template) prints `check: ok`, exits 0.
5. For each of C1–C10, planting exactly that violation in a fresh install
   makes `check.sh` exit 1 and print a line containing `[C<n>]`; nothing else
   changes.
6. `tests-locked.sh` passes on an untouched locked set; fails with the
   documented kind for: a modified committed test, a test modified but
   unstaged, a test modified and staged, a deleted test, a new untracked test
   matching `TEST_GLOBS`, a new committed test matching `TEST_GLOBS`, a sha
   that isn't an ancestor of `HEAD`, a missing `Tests-locked-at` line.
7. `adapt.sh` with `TOOLS=claude,cursor,copilot,gemini,codex` writes the
   documented files; a second run reports no `wrote` lines; a hand-written
   `CLAUDE.md` (no marker) is skipped, not overwritten; an existing
   `.claude/settings.json` is never touched.
8. After `install.sh` + `adapt.sh` (claude), `check.sh` still prints
   `check: ok` (the generated adapters satisfy C8/C9).

## Amendment 1 (2026-09-23): changes found by the first pilot

The first end-to-end pilot (evals/pilots/2026-09-23-toy-repo.md) found gaps
the original contract allowed. These amend the sections above; where they
conflict, this amendment wins.

**A1 — `tests-locked.sh` locks every existing test, not only the listed ones.**
If `TEST_GLOBS` is set, every file matching it *at the lock sha* is locked in
addition to the `## Locked tests` list: modified or deleted (compared exactly
as listed files are) fails with `LOCK modified: <path>` / `LOCK deleted:
<path>`. The success line counts all locked files (listed plus matched, each
counted once). Without `TEST_GLOBS`, only the listed files are locked, as
before. Rationale: the pilot weakened a pre-existing regression test and the
gate passed.

**A2 — `check.sh` fails on an unfilled install.**
- C11: a required `.cortex/config` key (`PROJECT_NAME`, `BUILD_CMD`,
  `TEST_CMD`, `LINT_CMD`, `TEST_GLOBS`, `TOOLS`) is unset, empty, or a
  `<...>` placeholder. One line per key:
  `FAIL [C11] .cortex/config: <KEY> is not set`.
- C12: `AGENTS.md` still contains the text `TODO`.
  `FAIL [C12] AGENTS.md: ...`.
Consequence for acceptance criterion 4: `check: ok` requires a filled
config (all six keys set to non-placeholder values) and an `AGENTS.md`
without `TODO`. A fresh, unfilled install now fails C11 and C12, and only
those.

**A3 — `adapt.sh` with `TOOLS` unset** (empty or placeholder) prints
`warning: TOOLS is not set in .cortex/config; no adapters written` and exits 0.

**A4 — new `scripts/cortex/gates.sh <change-folder>`** runs, in order:
`tests-locked.sh <change-folder>`, then `BUILD_CMD`, `TEST_CMD`, `LINT_CMD`
from `.cortex/config` (each via `bash -c`, from the repo root), then
`check.sh`. Every step runs even if an earlier one failed. For each step it
prints `gate <name>: ok` or `gate <name>: FAIL (exit <n>)`, where name is
`tests-locked`, `build`, `test`, `lint`, `check`; the output of a failing
step is printed above its line. A required command that is unset fails as
`gate <name>: FAIL (not set in .cortex/config)`. Final line `gates: ok`
(exit 0) or `gates: <n> failed` (exit 1). Usage error (no argument) exits 2.
The config is the repository's own file, so running its commands is the
point, but the script never `source`s it. Rationale: the pilot found
`BUILD_CMD`/`TEST_CMD`/`LINT_CMD` were read by nothing, and each command
restated them by hand.

**A5 — `install.sh` also installs the design rules.** It copies cortex's
`docs/01-design-rules.md` to `<target>/.cortex/design-rules.md` under the
same absent/unchanged/skipped rules as template files (reported with that
relative path), so the rule IDs the installed commands cite resolve inside
the repository. The summary counts it like any other file (a fresh install
creates template files + design rules + version).

### Amended acceptance criteria

9. Editing, deleting, or `git add`-ing a change to a pre-existing test that
   matches `TEST_GLOBS` but is not in the `## Locked tests` list fails
   `tests-locked.sh` with `LOCK modified` / `LOCK deleted`; without
   `TEST_GLOBS` it passes.
10. A fresh, unfilled install fails `check.sh` with C11 (once per unset key)
    and C12, and nothing else; filling the config and removing `TODO` from
    `AGENTS.md` gives `check: ok`.
11. `adapt.sh` with `TOOLS` unset prints the warning and writes nothing.
12. `gates.sh` reports each of the five gates, runs all of them after a
    failure, fails a missing command, and exits 0 only when all pass.
13. A fresh install contains `.cortex/design-rules.md` identical to cortex's
    `docs/01-design-rules.md`, reported as `created .cortex/design-rules.md`.

## Amendment 2 (2026-09-24): changes found by the final review

An independent review of the whole branch reproduced ways to defeat the
test lock and several portability gaps. These amend everything above.

**B1 — The lock record is its own file and can't be moved.** `tests-locked.sh`
reads `<change-folder>/lock.md` (same format as before: a
`Tests-locked-at: <sha>` line and a `## Locked tests` list), not
`tasks.md`. `test-first` commits the tests (commit T), then adds `lock.md`
naming T in a second commit L. The script fails with `LOCK moved: <detail>`
unless: exactly one commit in `git log` touches `lock.md` (commit L); L's
first parent is the sha in the file; and `lock.md` in the working tree and
index is identical to L's version. Rationale: the reviewer edited
`tasks.md` to point the sha at HEAD after weakening a helper, and the gate
passed. `LOCK missing` covers a missing `lock.md`. List lines may carry a
trailing note after the path (``- `path` (new)``): when the line contains a
backticked path, that is the path; otherwise the path is the first word.

**B2 — The config the lock applies to is the one at the lock.**
`TEST_GLOBS` is read from `git show <sha>:.cortex/config`, not the working
tree. `.cortex/config` is itself locked: if it differs between the sha and
the working tree (committed, staged or unstaged), fail with
`LOCK modified: .cortex/config`. This also freezes the gate commands
`gates.sh` runs for the duration of the change. It counts in the success
line's file count only if it existed at the sha.

**B3 — Portable invocation.** `gates.sh` runs the other scripts as
`bash <path>`, so a lost executable bit (a Windows commit with
`core.filemode=false`) can't break it. The template ships a `.gitattributes`
containing `*.sh text eol=lf`. `install.sh`, when the target's
`core.filemode` is `false`, prints
`note: this repository ignores file modes; after committing, run git update-index --chmod=+x scripts/cortex/*.sh`.

**B4 — Paths are handled byte-exactly.** Every git call that lists paths in
`tests-locked.sh` uses `-c core.quotepath=off`, so non-ASCII and spaced test
paths lock and compare like any other.

**B5 — `check.sh` C1 matches whole words** (`grep -w`), so a project named
like a common word (Cortex, Spec, Git) can pass. C8 allows only the exact
comment `<!-- cortex:generated -->` besides `@AGENTS.md` (any other
comment could hide instructions).

**B6 — `install.sh` refuses a mixed-version install and a non-root target.**
- If `<target>/.cortex/version` exists and differs from `VERSION`: print
  `error: this repository has cortex <old> installed; upgrading to <new> is not supported yet (see docs/02-extensions.md §4)`
  to stderr, copy nothing, exit 2.
- If `<target>` is not the root of its git work tree: error to stderr, copy
  nothing, exit 2 (the other scripts resolve paths from the root).

**B7 — `adapt.sh` reports what it didn't touch.**
- `.claude/settings.json` identical to its source prints
  `unchanged .claude/settings.json` (not the merge message).
- For each known tool not in `TOOLS` whose generated file exists and carries
  the marker (`CLAUDE.md`, `.cursor/rules/cortex.mdc`,
  `.github/copilot-instructions.md`, `GEMINI.md`), print
  `stale <path> (<tool> is not in TOOLS; delete it if unused)`. Never delete.

### Amended acceptance criteria

14. After the lock, each of these fails `tests-locked.sh`: editing
    `lock.md` (unstaged, staged, committed) → `LOCK moved`; a second commit
    touching `lock.md` → `LOCK moved`; a `lock.md` whose commit's parent is
    not the named sha → `LOCK moved`; editing `.cortex/config` (e.g.
    narrowing `TEST_GLOBS`) → `LOCK modified: .cortex/config`; narrowing
    `TEST_GLOBS` in the working tree does not un-lock a matched test.
15. A locked test at a path with spaces and at a non-ASCII path passes when
    untouched and fails when edited.
16. CRLF line endings in `lock.md` and `.cortex/config` parse the same as LF.
17. `gates.sh` works when the scripts have lost their executable bit, and
    from a subdirectory with a relative change-folder path.
18. C1 does not fire for a project name that appears only inside another
    word; C8 fires for a second, different HTML comment.
19. `install.sh` exits 2 and copies nothing for a version mismatch and for a
    non-root target; prints the filemode note when `core.filemode=false`;
    installs `.gitattributes`.
20. `adapt.sh` reports `unchanged .claude/settings.json` on a re-run and a
    `stale` line for a removed tool's generated file, deleting nothing.

Criteria 6's `tasks.md` cases now apply to `lock.md`; the earlier
"version mismatch warns and keeps the file" and "target inside a git work
tree is accepted" behaviors are replaced by B6.

## Amendment 3 (2026-09-24): the server-side boundary

Three independent reviews each found new ways to defeat the local test lock
(rewriting history, `--skip-worktree`, editing the checker, narrowing the
test command). A check that runs on the same machine as the agent it checks
can't be a boundary, so this amendment moves enforcement where industry
practice puts it: CI on the pull request, from a fresh checkout, with the
checker taken from the base branch, plus required human review (CODEOWNERS)
for tests, lock records and harness files. The local scripts stay as
guardrails.

**C1 — new `scripts/cortex/ci-gates.sh <base-ref>`**, run from anywhere
inside the repository; usage error (no argument, or a ref that doesn't
resolve) exits 2.

1. Scripts come from the base: if `<base-ref>:scripts/cortex/gates.sh`
   exists, every `scripts/cortex/*.sh` at `<base-ref>` is extracted to a
   temporary directory and used, and it prints
   `ci-gates: using scripts from <base-ref>`. Otherwise (the change that
   installs cortex) it uses the working tree's copy and prints
   `ci-gates: note: <base-ref> has no cortex scripts; using this branch's copy`.
2. Hidden edits: if any tracked file has git's skip-worktree or
   assume-unchanged flag (`git ls-files -v` shows `S` or a lowercase letter),
   print `ci-gates: FAIL hidden <path>` for each and count one failure per
   file.
3. Runs the base copy of `check.sh` on the repository root; prints
   `ci-gates: check ok` or `ci-gates: FAIL check`.
4. For each change folder whose `lock.md` exists now and differs from
   `<base-ref>` (added or changed on this branch; found with
   `git diff --name-only <base-ref>...HEAD`), runs the base copy of
   `gates.sh <folder>`, prints its output, then `ci-gates: <folder> ok` or
   `ci-gates: FAIL <folder>`.
5. Final line `ci-gates: ok` (exit 0) or `ci-gates: <n> failed` (exit 1).
   Every step runs even after a failure.

**C2 — template CI and ownership files** (content, not scripts):
`template/.cortex/ci/github/cortex.yml` (a GitHub Actions workflow: on every
pull request, a full-history checkout and `bash scripts/cortex/ci-gates.sh
origin/<base branch>`; actions pinned to commit SHAs) and
`template/.cortex/ci/github/CODEOWNERS` (owners for test paths, `changes/**/lock.md`,
`.cortex/`, `scripts/cortex/`, `harness/`, `docs/constitution.md` and
`.github/`). INSTALL.md copies them into `.github/` with the user and lists
the branch-protection settings that make them binding.

### Amended acceptance criteria

21. With pristine scripts at the base and, on the branch, a
    `tests-locked.sh` edited to exit 0 plus a weakened locked test,
    `ci-gates.sh <base>` fails with the base copy's `LOCK modified`, while
    the branch's own `gates.sh` passes.
22. With no cortex scripts at the base, it prints the note and uses the
    branch copy.
23. Only change folders whose `lock.md` changed relative to the base are
    gated; with none, only the check runs, and a clean repository ends
    `ci-gates: ok`.
24. A tracked file marked skip-worktree or assume-unchanged fails with
    `ci-gates: FAIL hidden <path>`.
25. No argument, or an unresolvable ref, exits 2.

## Amendment 4 (2026-09-24): keeping a locked branch up to date

The pre-merge completeness audit reproduced two ways the lock blocks
legitimate work: bringing a change branch up to date with its base after
the lock (a merge of the base that touches a locked or `TEST_GLOBS` file
reads as `LOCK modified` / `LOCK added`), and archiving a finished change
folder under `changes/archive/` (`ci-gates.sh` then gates the moved
`lock.md` and reports `LOCK moved`).

**D1 — merging the base is allowed; rebasing is not.** In
`tests-locked.sh`, a locked path (listed, matched by `TEST_GLOBS` at the
sha, or `.cortex/config`) that differs from the sha is **not** a failure
when its current content (working tree and index both) is identical to its
content at the *second parent* of some merge commit in
`git log --first-parent --merges <sha>..HEAD`: the branch took the base's
version of that file wholesale. Likewise a file matching `TEST_GLOBS` that
did not exist at the sha is **not** `LOCK added` when it exists, with
identical content, at such a second parent. Any other difference still
fails as before, including a merge that resolves a locked file to content
matching neither side. Rebasing after the lock remains unsupported: the
sha is no longer an ancestor (`LOCK bad-sha`). The success line is
unchanged.

**D2 — archived change folders are not gated.** `ci-gates.sh` ignores
lock files under `changes/archive/` when choosing which folders to gate,
and `retro.md` says how to archive a finished change (`git mv` its folder
under `changes/archive/`, in its own commit, after the change merged).

### Amended acceptance criteria

26. After the lock, a merge of a base in which a locked test, a
    `TEST_GLOBS`-matching file, or `.cortex/config` changed (and a new
    `TEST_GLOBS` file was added) passes `tests-locked.sh` when the merge
    took the base's versions.
27. On top of such a merge, editing that same locked file on the branch
    fails with `LOCK modified`; a merge that resolves it to content differing
    from both the base and the sha fails with `LOCK modified`.
28. A rebase of the branch onto a moved base still fails with
    `LOCK bad-sha` or `LOCK moved`.
29. With a folder moved under `changes/archive/` on the branch,
    `ci-gates.sh` does not gate it and ends `ci-gates: ok` when nothing else
    fails.

## Amendment 5 (2026-09-25): install.sh without per-file processes

`install.sh` started `mkdir`, `cp` and `cmp` once per template file, so its
cost grew with the template: a fresh install of 45 files took 21.5 s and a
re-run 10.5 s on a Windows machine (process start-up there costs 10–50 ms),
and `install.test.sh` alone spent minutes inside it. This amendment changes
how the script works, not what it does.

**E1 — behavior unchanged.** Every requirement in "`scripts/install.sh`"
and A5/B3/B6 still holds: the same `created` / `unchanged` / `skipped` lines,
in the same sorted order, the same summary line, the same refusals and exit
codes, the design-rules and version files, the file-mode note, executable
`*.sh` files, and never overwriting, deleting, or running a writing git
command.

**E2 — a bounded number of processes.** The number of times `install.sh`
runs `cp`, `cmp`, `mkdir` and `chmod` does not grow with the number of
template files: each is run at most 3 times per install, whether the target
is empty (everything created) or already fully installed (everything
unchanged). Bulk operations (for example one `tar` pass to copy new files,
one `git hash-object` call per side to compare existing ones) are allowed;
`tar` and `git` are the only tools this adds, and both are already present
wherever cortex runs.

### Amended acceptance criteria

30. With `cp`, `cmp`, `mkdir` and `chmod` shimmed on `PATH` to count their
    calls (and then run the real command), a fresh install and a full
    re-run each call every one of them at most 3 times, and every existing
    install test still passes unchanged.
31. A template file whose name contains a space is installed, compared and
    reported like any other (`created "<path>"` is printed with the path as
    is, no quoting).

## Amendment 6 (2026-09-30): one config parser

Four scripts (`check.sh`, `gates.sh`, `tests-locked.sh`, `adapt.sh`) each
carried their own copy of the `.cortex/config` parser, and the copies had
already diverged in how they handled whitespace. The parser is the input to
every gate, so it gets one source. This amendment changes where the parsing
lives, not what any script does.

**F1 — one parser, next to its callers.** `scripts/cortex/_config.sh` is a
file that is sourced, never run, and does nothing when sourced but define
`config_value KEY`: it reads config text on stdin and prints the value of
`KEY` as the "`.cortex/config` format" section defines it (CRs removed;
comment lines and lines without `=` skipped; key and value trimmed of
surrounding whitespace; the first line with that key wins; a `<...>` value
prints nothing). `check.sh`, `gates.sh`, `tests-locked.sh` and `adapt.sh`
read every config value through it, and each sources the copy in its own
directory, the way `gates.sh` finds its sibling scripts: a base-branch copy
of a script run by `ci-gates.sh` uses the base-branch parser, never the
branch's. The config is still parsed, never sourced or executed.

**F2 — behavior unchanged.** Every earlier requirement still holds.
`adapt.sh` still removes all whitespace from `TOOLS` after parsing, so

## Amendment 9 (2026-10-03): a signed re-lock

`implement.md` tells the implementer that a locked test that looks wrong is a
spec problem and "the user decides whether `test-first` re-runs". But
`test-first.md` says `lock.md` is never edited again, and `tests-locked.sh`
reports `LOCK moved` as soon as a second commit touches it, so a re-run
can't produce a lock the check accepts: a change stuck on a wrong test can
only start over. This amendment makes the re-run possible without reopening
the cheat the single-commit rule prevents (an implementer committing weakened
tests, then a lock commit naming them).

**K1: a lock may be renewed, with the user's sign-off.** `lock.md` may carry
a line `Re-lock signed off by: <text>`. The commits that touch `lock.md`,
oldest first, are the lock commits. Each one's first parent must be the commit
its `lock.md` names in `Tests-locked-at:`, as Amendment 2's single lock already
requires; every lock commit after the first must have a sign-off line whose
text is non-empty and not a `<...>` placeholder. A lock commit that breaks
either rule fails with `LOCK moved: <detail>`, and so do uncommitted edits to
`lock.md`, as before. The first lock commit needs no sign-off. The
sign-off line may sit anywhere in `lock.md` (the first one counts); text
that is only spaces is empty, and a placeholder is text that starts with `<`
and ends with `>`. Uncommitted edits include staged ones. The check proves a
sign-off exists, not who wrote it: the sign-off is free text, as the
approval line is, so the safeguard against a forged one is a person reviewing
the test and config content in the pull request (branch protection with
Code Owners on the test paths), and the local check stays a guardrail
(R11).

**K2: the newest lock governs.** The newest lock commit's `lock.md` (which
must equal the working tree's) supplies `Tests-locked-at`, the
`## Locked tests` list, the `TEST_GLOBS` read from `.cortex/config` at that
commit, and the config itself; the merges Amendment 4 accepts are those after
that sha. Everything else is as before.

**K3: the field never trips C7.** The sign-off field is not named
`Approved-by:`, so the `lock.md` template under `harness/` keeps C7 passing;
it is distinct from a spec's approval.

### Amended acceptance criteria

50. A signed re-lock passes: after T1 and L1 (as Amendment 2), further commits,
    then T2 (test edits) and L2 (`lock.md` naming T2, listing its files, with
    `Re-lock signed off by: <a name>`), `tests-locked.sh` exits 0 and its
    success line names T2's short sha.
51. An unsigned re-lock fails: the same as 50 but L2 has no sign-off line, or
    an empty one, or `<name>` → `LOCK moved`, exit 1.
52. A re-lock whose commit's first parent is not the sha it names fails with
    `LOCK moved`, even when signed.
53. After a signed re-lock, a later commit that edits `lock.md` again without
    a sign-off (for example, removing it) fails with `LOCK moved`.
54. After a signed re-lock, the lock is T2's: a file listed in L2 or matching
    `TEST_GLOBS` at T2, edited afterwards → `LOCK modified`; a new file
    matching `TEST_GLOBS` added after T2 → `LOCK added`; a test file changed
    between L1 and T2 and locked again at T2 → no failure.
55. After a signed re-lock, merging the base (a locked file taking the base's
    version whole, as Amendment 4) is accepted.
56. Every earlier `tests-locked.sh` criterion still holds; in particular a
    single lock commit passes with or without a sign-off line, and a second
    lock commit without one still fails as criterion 14 says.

## Amendment 10 (2026-10-03): closing the lock's merge and re-lock holes

The pre-release audit of 2.1.0 (`evals/audits/2026-10-03-2.1.0.md`) found
that Amendment 9's re-lock blesses earlier tampering, and two bypasses that
exist since 2.0.0. This amendment corrects Amendment 9 and closes them.
Where it conflicts with K2 or criterion 54, it wins.

**L1: a re-lock blesses only its own tests commit.** For each lock commit
after the first, naming T_i, the previous lock (naming T_(i-1)) must still
hold at T_i's first parent, comparing committed content: every file it
locked (its list, the files matching `TEST_GLOBS` at T_(i-1), and
`.cortex/config`) has its content at T_(i-1), or a version accepted from the
base (Amendment 4, as limited by L3), and no file matching that
`TEST_GLOBS` was added. A violation is reported as `LOCK modified` or
`LOCK added` for the file, as if the re-lock had not happened. Only what
T_i itself changes is blessed by the sign-off.

**L2: lock history is the branch's own.** Lock commits are the commits on
`HEAD`'s first-parent line that change `lock.md` relative to their first
parent. A merge on that line whose `lock.md` differs from its first parent's
is a lock commit and fails K1 (its first parent is not the sha it names), so
a lock brought in by merging another branch is `LOCK moved`.

**L3: the base allowance needs the base.** When `CORTEX_BASE_REF` is set (a
ref or sha), Amendment 4 accepts a locked file's version only from a merged
parent that is an ancestor of that ref; a version from any other merged
parent counts as an edit. `ci-gates.sh` sets `CORTEX_BASE_REF` to its
base-ref argument for every gate it runs. When it is unset (local runs),
Amendment 4 applies unchanged: any merged parent's version is accepted, and
the local check stays a guardrail (R11).

**L4: a re-lock keeps the earlier list, and a missing lock fails cleanly.**
Every path the previous lock listed must be listed again; a dropped one is
`LOCK moved`. A lock commit in which `lock.md` doesn't exist (deleted, then
re-added later) is `LOCK moved`, exit 1, never a git error. Once `lock.md`
has been deleted the check has already failed; a lock commit after the
deletion is not compared with any lock before it.

### Amended acceptance criteria

57. Replaces criterion 54's third clause: after L1, a commit edits a locked
    test (and, separately, `.cortex/config`); then T2 changes a different
    test and a signed L2 names T2 → `LOCK modified` for the file edited
    before T2, exit 1. A file changed in T2 itself is accepted, as before.
58. A file matching `TEST_GLOBS` added after L1 and before T2, not in T2's
    own changes → `LOCK added` after a signed re-lock.
59. A side branch from T1 that commits tests and a `lock.md` naming them,
    merged into the locked branch (taking the side's `lock.md`) → `LOCK
    moved`, exit 1, whether or not that `lock.md` is signed.
60. With `CORTEX_BASE_REF` set to the base: a locked test weakened on a side
    branch (not reachable from the base) and merged into the locked branch,
    `lock.md` untouched → `LOCK modified`, exit 1; a merge of the base
    itself (Amendment 4's fixture) still passes.
61. With `CORTEX_BASE_REF` unset, Amendment 4's behavior is unchanged
    (every existing merge case passes).
62. `ci-gates.sh`: a pull request whose branch merges a side branch that
    weakened a locked test fails (the base copy of `gates.sh` runs the lock
    with `CORTEX_BASE_REF` set to the base ref).
63. A signed re-lock that drops a path the previous lock listed → `LOCK
    moved`.
64. A lock commit in which `lock.md` is deleted (re-added later) → `LOCK
    moved`, exit 1, with no git error.

## Amendment 11 (2026-10-03): no merge allowance; the lock can't be dropped

Each audit of 2.1.0 found a new way through Amendment 4's allowance for a
locked file that a merge changes (H3b, then a merge restoring a file's
pre-lock version, which then vanishes from the pull request's diff). R11
warns that a rule narrowed by reasoning about input shapes opens bypasses
that only probing finds, so the allowance is withdrawn, not narrowed again.
Amendment 9's signed re-lock replaces it. Where this amendment conflicts with
Amendment 4 (D1, criteria 26-27), Amendment 9 (criterion 55's merge after a
re-lock, and a re-lock that changes `TEST_GLOBS`) or Amendment 10 (L3,
criteria 60-61), it wins; those are withdrawn.

**M1: no merge allowance.** A locked file, or `.cortex/config`, whose content
differs from the newest lock's sha is `LOCK modified` (or `deleted`, or a
new matching file `LOCK added`), however it changed, merges included. The
same holds inside a re-lock window (Amendment 10, L1). `CORTEX_BASE_REF` is
no longer read, and `ci-gates.sh` no longer sets it.

**M2: bringing a locked branch up to date is a re-lock.** Merge the base;
if the merge changed locked files, re-lock: the merge commit is the re-lock's
tests commit (T_i), and `lock.md` naming it, with the user's sign-off, is the
very next commit. The sign-off blesses what the merge changed. A merge that
changed no locked file needs nothing.

**M3: a re-lock may not change the config.** A re-lock whose tests commit
changes `.cortex/config` relative to the previous lock's sha is
`LOCK modified: .cortex/config`, so `TEST_GLOBS` and the gate commands stay
as locked for the whole change. This holds for a re-lock of a base merge too: if the base
changed `.cortex/config` while a change is locked, that change can't take the
base in; it is finished without it or started over from the new base (a
rare case, and the price of a config nothing can loosen mid-change).

**M4: a branch can't drop its own lock in CI.** `ci-gates.sh` fails, for a
folder, when the branch adds a `lock.md` (the base has none at that path)
and that `lock.md` no longer exists at `HEAD`, whether deleted or moved
(for example under `changes/archive/`). Archiving a folder whose `lock.md`
is already on the base stays ungated (Amendment 4, D2). CI runs on a fresh checkout, so
"at `HEAD`" means the commit; the line is
`ci-gates: FAIL <folder> (lock.md added on this branch is gone)`.

### Amended acceptance criteria

65. After the lock, merging a base that changed a locked test, the config,
    or added a matching file, with no re-lock → `LOCK modified` (or
    `LOCK added`), exit 1, with or without `CORTEX_BASE_REF`.
66. The same merge, then a signed re-lock naming the merge commit (its
    `lock.md` committed as the very next commit) → exit 0, and the success
    line names the merge commit.
67. A merge from the base resolved by taking the base's older copy of a
    locked test (the base never changed it) → `LOCK modified`.
68. A fabricated merge whose second parent is the fork point, restoring a
    locked test's pre-lock content → `LOCK modified`.
69. A signed re-lock whose tests commit changes `.cortex/config` (for
    example narrowing `TEST_GLOBS`) → `LOCK modified: .cortex/config`.
70. `ci-gates.sh`: a branch that adds a lock and then deletes it, or moves
    its folder under `changes/archive/`, fails for that folder; a branch
    that archives a folder whose `lock.md` is on the base still passes
    (criterion 29).
71. Criteria 57-59, 62 and 63-64 still hold; criteria 26-27 and 60-61 are
    withdrawn.

## Amendment 12 (2026-10-04): every commit the branch brings counts

The third audit of 2.1.0 found that a merge can drop a lock past Amendment
11's M4 without a force-push: a merge whose first parent predates the lock
and whose second parent is the lock commit, keeping the first parent's tree
for the change folder, leaves no `lock.md` at `HEAD`. `git log` with a
pathspec simplifies history by default and prunes the merged side as
identical to the first parent for that path, so the lock commit is never
seen and nothing is gated. The locked tests then vanish from the pull
request's diff, so no reviewer sees them either.

**N1: M4 reads every commit the branch brings.** The commits M4 inspects are
all those reachable from `HEAD` and not from the base, on every side of every
merge, with no history simplification, and a merge counts as changing what
differs from any of its parents. A `lock.md` that any of them adds or
changes, that the base doesn't have and `HEAD` doesn't have, fails as M4
says. (Criterion 62 holds as Amendment 11 left it: the gates run without
`CORTEX_BASE_REF`, which nothing reads.)

**N2: what the lock can't see (known limits, not checked).** Both leave the
weakened tests visible in the pull request's diff, so the safeguard is the
human review of test paths that Amendment 9's K1 already relies on.
- History that never reaches CI: a force-push that removes the lock commits
  before the pull request is opened leaves nothing to inspect. M4 holds for
  history as pushed.
- A rebuilt first-parent line: weaker tests and a first `lock.md` naming
  them, committed from before the real lock, then merged with the real lock
  (keeping the rebuilt `lock.md`), is a first lock, which needs no sign-off.
  It is K1's forged lock without even a sign-off line to notice.

### Amended acceptance criteria

72. `ci-gates.sh`: a branch whose tip is a merge with first parent a commit
    before the lock (no `lock.md`) and second parent the lock commit, whose
    tree has no `lock.md` for that folder → `ci-gates: FAIL <folder>
    (lock.md added on this branch is gone)`, exit 1. It fails too when the
    folder ends up under `changes/archive/`, whether the merge itself moves
    it or the first parent (a commit after the tests, with no `lock.md` at
    the folder's own path) already holds the archived copy and the merge
    keeps that parent's tree.
73. Criterion 70's cases still hold: a folder whose `lock.md` is on the base
    and is archived on the branch passes, and a branch whose lock stays at
    `HEAD` is gated as before.
74. `ci-gates.sh`: a `lock.md` that only merges touch: a merge (first parent
    the tests commit) adds `changes/x/lock.md`, which neither parent has,
    and a later merge removes it, with no ordinary commit on the branch
    touching that path → `ci-gates: FAIL changes/x (lock.md added on this
    branch is gone)`, exit 1.
